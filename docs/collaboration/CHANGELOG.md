# Development Changelog

_Last updated: 2026-10-05_

Meaningful changes that other developers and Claude sessions need to know about. This is **not** a copy of Git history.

Record a change here when it:

- changes what another developer must do (new setup step, new environment variable, new command, new migration);
- changes a shared contract, module boundary, or convention;
- completes, blocks, or unblocks a phase or task;
- records an accepted ADR or an owner decision.

Don't record routine commits, refactors with no external effect, or test-only changes.

Format: newest first, one short line per change with its task and PR or commit. Unmerged work goes under **Unreleased**.

## Unreleased

- **Homepage visual redesign (PR #45):** the reference design, ported onto current `develop` rather than cherry-picked. The three original redesign commits were based on a pre-UI-3 tree, so their combined diff would have deleted UI-3 to UI-6; the homepage files were taken at their final state and the stylesheet was composed section by section — twelve shared sections were byte-identical, and `header`, `buttons` and `reservation` were resolved individually so `.button--quiet`, `.notice--info` and `.notice--success` survived. The shell (`layout.tsx`) changed with it, so every page now carries the lighter header and footer. New components: `Scene` (drawn art, with a commented-out photo map awaiting **O14**), `DrawCountdown`, `DrawRowCard`, `icons`; `VaultEmblem` removed as unused. `BrandMark` is now a stag. **Unsupported claims were removed rather than softened**: an invented winner count, two review scores, a Trustpilot rating, a registered address, social links, five fabricated instant-prize amounts and three inline guarantees are gone, and the category cards now mark four of five categories "Coming soon" because no category system exists. What replaced them states how the product works and is checkable in the code. The root layout still sets `robots: { index: false }`, and a smoke test now asserts that tag so it cannot be dropped silently.

- **UI-6 (PR #44):** the payment experience. Every customer-facing state is keyed on the **order**, never the attempt or the URL: pending, paid, `paid_unfulfillable`, expired, cancelled and refunded each have their own wording, and a derived state covers the minute between a deadline passing and the expiry sweep recording it. Pending payments now resolve without a manual reload — a client component polls the read-only status route and then asks the **server** to re-render, so it has no wording for `paid` and cannot invent one; with scripting off it never runs and the page is unchanged. A new web route handler proxies that read because the browser never calls the API (ADR-0009). Attempt expiry and order expiry are kept distinct, and a refused payment offers "Try again" through the existing initiation flow. The cancel page links back to the order only when the access cookie proves which order it is. **No payment behaviour changed**: the port, webhook intake, finalisation, reconciliation, the expiry worker, refunds and order-access handling are untouched, and a browser test now drives a signed webhook through the real endpoint to prove a genuinely paid order renders.

- **UI-5 (PR #42):** checkout. The refusal map was a `Record<string, string>` that had drifted from the API in both directions — six of its keys were not in `ErrorCode` at all and were emitted nowhere, while the codes the API really sends had no entry, so a wrong skill answer reached the customer as "Something went wrong". The codes now `satisfies readonly ErrorCode[]` and the map is total over them, so drift fails the build; the wording for a refused answer stays deliberately identical for a wrong answer and a missing one (ADR-0030). One render now mints one idempotency key and the form carries it, so a second click replays the order already made instead of being told the basket is empty. Presentation rebuilt on the existing `.option` rows; `.notice--info` and `.notice--success` defined, having been named by five pages with no rule behind them.

- **UI-4 (PR #41):** the basket. Each line is a live hold, so it shows its own countdown, and a lapsed line stays visible, is marked, and is excluded from the total. The summary prints `totalMinor` and `activeItemCount` **as the API gives them** — it never sums the lines, because the lines a customer can see and the lines the API will sell are not always the same set. No quantity controls: adding a draw already in the basket is a conflict by design. `.button--quiet` and `.page` were defined, both named by several pages with no rule behind them, and the nested `<main>` landmarks on checkout and the order page were removed while the two payment pages gained the `id` the skip link had always pointed at.

- **UI-3 (PR #40):** the competition detail page — prizes, the skill question, timings, cap and availability, all from `GET /markets/:market/draws/:slug`, with no invented statistics or urgency. Prize photography remains blocked by **O14**, so `PrizeArt`'s placeholder is framed rather than hidden.

- **UI-2 (PR #38):** the competition listing. Search, status filtering and sorting are **web-layer** work because the listing endpoint rejects query strings, and the toolbar is a GET form so the result is shareable and works without scripting. A `loading.tsx` was deliberately removed: its Suspense boundary streamed the results in after the shell, and without scripting they never arrived.

- **UI-1 (PR #37):** the product homepage, replacing the developer index. Draws come from the API across every open market, the market gate reaches the front page, and the API health readout is no longer published publicly.

- **P6-9 (WP-3):** **The customer payment-status GET is read-only** ([ADR-0035](../adr/0035-customer-payment-status-is-read-only.md)). `GET /markets/:market/checkout/orders/:order/payments/:payment` used to run a trusted provider status check whenever the attempt was `pending` or `processing`. That check calls the provider and then `finalization.confirm` — the same code a verified webhook reaches — so a customer refreshing their own page could capture a payment, sell tickets, release holds, raise a refund, write `order.*` outbox rows that become email, and write `payment.anomaly_detected` audit rows. It now reads `payments` and `orders` and returns them. **Everything protecting it is unchanged**: `@Public({ identify: true })`, `MarketGuard`, ownership (someone else's order is a 404), the guest fresh-verified-email requirement, the attempt/order consistency check, `paymentStatusPerOwner` consumed first and fail-closed, and the provider reference never leaving the server. **Payment advancement is unchanged and untouched**: the verified webhook remains authoritative and the P6-5 reconciler remains the recovery path, and two tests assert the same payment still settles by each after any number of customer reads. **No `POST …/check` replacement was added** — nothing calls one, and the staff route `POST admin/markets/:market/orders/:order/payments/:payment/reconcile` already provides a deliberate, MFA-gated, audited way to ask the provider; that route is unchanged. The dead web helper `fetchPaymentStatus` was removed after confirming zero callers; the API route stays. No migration, no schema change. **K-3, K-c, O7, O9, O12 and O13 are untouched.**

- **P6-8:** Migration `0027_order_access_tokens` and the web purchase journey (OD-2; owner decisions **D18 = B**, **D19 = A**, **D19a**). **The web purchase journey moved from direct reservation to the basket**, deliberately: `POST /checkout/orders` builds an order from the caller's basket and the order must match it exactly (ADR-0032), so a hold taken by the old draw-page route could never become an order. The draw page's action is now **Add to basket** (`POST /markets/:market/cart/items`), which takes the same real hold through the same ticket engine under the same cap and locks — `CartService` already did this, and **no second reservation or basket mechanism was created**. New pages: `/[market]/basket`, `/[market]/checkout`, `/[market]/orders/[id]`, `/checkout/payments/[id]/return` and `/cancel`. The reservation detail page is kept and linked from each basket line, because the hold is real and its ticket numbers are worth showing. **The return link** is an opaque per-order token, SHA-256 in the database and nowhere else, delivered in the provider return URL, expiring at `orders.expires_at + 30 minutes` from its **own** configured value (`ORDER_ACCESS_TOKEN_TAIL_MINUTES`, never derived from the guest email window). It authenticates nobody, confers no session or cap identity, reaches one order, is **read-only**, and **cannot start a payment** (D18 = B). New route `GET /checkout/order-access`, `@Public()` without `identify`, rate limited per IP and fail-closed; the token travels in the `x-hv-order-access` header, and a Route Handler at `/checkout/payments/[id]/return/exchange` moves it out of the URL into an HttpOnly cookie and redirects to a clean address. **The read is strictly a read** (owner decision S2): presenting a link no longer runs a trusted status check, so it cannot reach `finalization.confirm` and therefore cannot capture a payment, sell a ticket, raise a refund or send email. Confirmation arrives by verified webhook or by the P6-5 reconciler. The existing authenticated `GET markets/:market/checkout/orders/:order/payments/:payment` is unchanged and may still trigger reconciliation; reviewing it is a P6-9 hardening item. **The browser is never payment authority:** nothing in the web flow can mark an order paid, and both the integration suite and a Playwright test prove that forged returns and repeated refreshes leave the order `awaiting_payment` with no ticket sold, after which a webhook settles it. `draws.spec.ts` and `reservations.spec.ts` were updated to follow the basket journey — coverage of allocation, ticket numbers, the cap, expiry, market isolation and authorization is unchanged. The fake provider now keeps the return URL captured at creation, as a real provider does on an idempotent retry. Run `pnpm db:migrate up` and `pnpm db:codegen`. Next free migration number: `0028`.

- **P6-7:** Migration `0026_market_payment_configs` and per-market provider selection (B10; owner decision **D17 = A**). **A payment provider is now a property of the MARKET, not of the deployment.** Until now the API built one provider from the environment and every consumer compared the payment in front of it against that single instance; `market_payment_configs` (one row per market, created by the migration) now names which provider a market settles through, and `PaymentProviderRegistry` resolves it for initiation, reconciliation and refunds. A market with no configuration **cannot take a payment** — the correct state everywhere until O13 is answered — and fails closed with the existing `PAYMENT_PROVIDER_UNAVAILABLE`. **`config_ref` is a reference, never a secret** (I15): credentials stay in the environment, and the table has no column that could hold one. **No provider is named in the schema** (Gate 4.9) — the CHECK describes a code's shape, not which codes exist. **Webhook resolution deliberately does NOT read the table**: it resolves by code from the environment alone, so the route cannot be used to enumerate which markets are configured, and P6-3's boundary is unchanged. New staff routes `GET`/`PUT /admin/markets/:market/payment-config` under `config.manage` (granted to `super_admin` alone), the write **sensitive** — step-up MFA, a reason, and an audit row in the same transaction. Test fixtures gain `configurePaymentsForTesting`, because an enabled market must now be configured to pay. Run `pnpm db:migrate up` and `pnpm db:codegen`. Next free migration number: `0027`.
- **P6-5:** Migration `0025_payments_reconcile_permission` and the reconciliation slice (OD-5, D12a, D13a, and owner decisions K-a/K-b/K-c). The **internal listener** — a second Fastify socket on `INTERNAL_API_HOST`/`INTERNAL_API_PORT`, one route, guarded by `INTERNAL_API_TOKEN` compared in constant time — lets the worker have a payment re-checked without ever holding a provider credential. The public listener has no such route at all. The worker gains the **60-second reconciler** (5-minute lookback on `payments.updated_at`), **order expiry** (`awaiting_payment → expired`, emitting `order.expired`), **attempt expiry** (live → `expired`, order untouched), and **refund retry**. Handlers are registered for **all four `order.*` topics**; nothing emits `order.payment_failed`, because what makes an order failed is **K-c, still OPEN**. New permission `payments.reconcile` (sensitive) and the staff payment surfaces: view attempts/events/refunds under `orders.read`, and reconcile, open a sealed payload, and refund a duplicate capture under `payments.reconcile`. **New required environment variables:** `INTERNAL_API_TOKEN` (≥32 bytes, API) and `INTERNAL_API_URL` + `INTERNAL_API_TOKEN` (worker, required in production). See `.env.example`.
- **P6-4:** Migrations `0022_sale_requires_live_hold`, `0023_refunds` and `0024_expired_order_unfulfillable`, and atomic payment finalization (**Gate 4**). One transaction turns a verified provider success into sold tickets: order locked, amount and currency re-checked against the order, holds locked and required live, `reserved → sold` **then** `hv_end_reservation(…, 'released')` (D9 = A), audit and outbox in the same transaction. `hv_tickets_guard` now refuses a sale from a hold that is not live (**D10 = B**), independently of the application. The owner's late-capture decisions **D21, D22.1–3 and D23** are implemented: an order can reach `paid_unfulfillable` with an automatic full refund to the original instrument, terminal payment attempts stay terminal, a second capture is recorded and never silently absorbed, and `expired → paid_unfulfillable` is the one transition `0024` adds. **`refunds` moved forward from P6-6 into P6-4**, because all three decisions need a refund at the moment finalisation decides. **ADR-0034** records that a late payment is never re-allocated tickets (C10 / D14 = A). Run `pnpm db:migrate up` and `pnpm db:codegen`.

- **P5-8:** Migrations `0017_entrant_rekey` and `0018_cart_guard_bridged_entrant`, closing Phase 5. **ADR-0021 guest → account cap bridging is now implemented** — it never was: a guest could buy to the cap under their verified address and the account with that address could buy to it again. A guest allocation now resolves the address to an account **inside the allocating transaction**, and registration moves whatever that address holds onto the new account, counters and live holds together. The holds have to move, because `hv_end_reservation` decrements using the key on the reservation — a counter that moved alone would be decremented by a `WHERE` matching zero rows, silently and for ever. Hence `0017`, which relaxes `hv_reservations_guard` by exactly one case (`email → user`, onto a real account, active holds only), and `0018`, which teaches `hv_cart_items_guard` that a guest basket may now legitimately hold an account-keyed reservation. **The ticket engine now takes one advisory lock** (`lockEntrantEmail`), taken by guest allocation and registration, because row locks cannot serialise a row that does not exist yet — ADR-0011 is amended to record it. **Checkout is rate limited** (B19): `checkoutPerOwner`, 30 per 10 minutes per checkout identity, fail-closed; it bounds checkout attempts and is **not** an answer-attempt counter, which ADR-0030 deliberately does not introduce. Run `pnpm db:migrate up`. Next free migration number: `0019`.

- **P5-7:** Migration `0016_orders` and order creation (B7, B18, B20; ADR-0030, ADR-0031). `orders` (`order_number` UNIQUE, `user_id` **or** `guest_email`, `terms_version_id`, `total_minor = wallet_applied_minor + external_due_minor`, `idempotency_key` UNIQUE) and `order_items` (draw, reservation, quantity and price snapshots, `skill_answer_option_id`), both **immutable** apart from the order's status. New route `POST /markets/:market/checkout/orders` plus `GET` for one and for the caller's own, all `@Public({ identify: true })` behind `MarketGuard`, so a verified guest can place an order **without an account**. **`Idempotency-Key` is required** and enforced by the database — `ON CONFLICT (idempotency_key) DO NOTHING`, no read-then-insert and no Redis — with a request digest so the same key used for a different request, or by a different customer, is refused rather than answered with the earlier order. A **wrong skill answer creates nothing at all** (ADR-0030): no order, no spent key, basket and hold intact, and the correct option never leaves the API. **`order_number` is `HV-` + 10 base32 characters**, random and never sequential (the length ADR-0031 left to this task). **Phase 5 ends here:** the order is `awaiting_payment`, the reservation stays active and its tickets stay `reserved`; payment, webhooks and `reserved → sold` remain Phase 6. Note the status name — B7 says `awaiting_payment` where the planning prose said "pending_payment"; the specification wins because Phase 6 implements its transitions literally. Run `pnpm db:migrate up` and `pnpm db:codegen`. Next free migration number: `0017`.

- **ADR-0032 — checkout request identity.** The specification does not define whether a checkout request describes the purchase or simply means "convert my basket", and the two readings disagree about what reusing an `Idempotency-Key` means. The owner settled it: **checkout requests are self-describing.** `CreateOrderRequest` now carries `items: [{ slug, quantity, optionId? }]` instead of `answers`, the server matches that intent against the locked basket and refuses a mismatch with a generic conflict, and the idempotency digest covers **market, buyer, terms version and the sorted draw/quantity/answer tuples** — so the same key used for a different quantity, draw, answer or terms version is refused rather than answered with the earlier order. The request remains **intent only**: price, currency, market, availability, ownership, eligibility and answer correctness still come from PostgreSQL. **No schema change** — migration `0016` is unchanged.

New routes: `GET /markets/:market/terms`, `POST …/terms/acceptance`, and admin `GET/POST /admin/markets/:market/terms` plus `…/:terms/publish` and `…/:terms/activate` (`markets.gate.manage`, sensitive, audited). **No legal wording is stored or invented** — there is no content column; the content is legal's and arrives in Phase 12. Accepting checks the version the customer saw against the active one, so a stale page cannot record agreement to wording nobody was shown. Run `pnpm db:migrate up` and `pnpm db:codegen`.
