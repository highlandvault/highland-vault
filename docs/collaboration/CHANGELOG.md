# Development Changelog

_Last updated: 2026-09-25_

Meaningful changes that other developers and Claude sessions need to know about. This is **not** a copy of Git history.

Record a change here when it:

- changes what another developer must do (new setup step, new environment variable, new command, new migration);
- changes a shared contract, module boundary, or convention;
- completes, blocks, or unblocks a phase or task;
- records an accepted ADR or an owner decision.

Don't record routine commits, refactors with no external effect, or test-only changes.

Format: newest first, one short line per change with its task and PR or commit. Unmerged work goes under **Unreleased**.

## Unreleased

- **P5-8:** Migrations `0017_entrant_rekey` and `0018_cart_guard_bridged_entrant`, closing Phase 5. **ADR-0021 guest → account cap bridging is now implemented** — it never was: a guest could buy to the cap under their verified address and the account with that address could buy to it again. A guest allocation now resolves the address to an account **inside the allocating transaction**, and registration moves whatever that address holds onto the new account, counters and live holds together. The holds have to move, because `hv_end_reservation` decrements using the key on the reservation — a counter that moved alone would be decremented by a `WHERE` matching zero rows, silently and for ever. Hence `0017`, which relaxes `hv_reservations_guard` by exactly one case (`email → user`, onto a real account, active holds only), and `0018`, which teaches `hv_cart_items_guard` that a guest basket may now legitimately hold an account-keyed reservation. **The ticket engine now takes one advisory lock** (`lockEntrantEmail`), taken by guest allocation and registration, because row locks cannot serialise a row that does not exist yet — ADR-0011 is amended to record it. **Checkout is rate limited** (B19): `checkoutPerOwner`, 30 per 10 minutes per checkout identity, fail-closed; it bounds checkout attempts and is **not** an answer-attempt counter, which ADR-0030 deliberately does not introduce. Run `pnpm db:migrate up`. Next free migration number: `0019`.

- **P5-7:** Migration `0016_orders` and order creation (B7, B18, B20; ADR-0030, ADR-0031). `orders` (`order_number` UNIQUE, `user_id` **or** `guest_email`, `terms_version_id`, `total_minor = wallet_applied_minor + external_due_minor`, `idempotency_key` UNIQUE) and `order_items` (draw, reservation, quantity and price snapshots, `skill_answer_option_id`), both **immutable** apart from the order's status. New route `POST /markets/:market/checkout/orders` plus `GET` for one and for the caller's own, all `@Public({ identify: true })` behind `MarketGuard`, so a verified guest can place an order **without an account**. **`Idempotency-Key` is required** and enforced by the database — `ON CONFLICT (idempotency_key) DO NOTHING`, no read-then-insert and no Redis — with a request digest so the same key used for a different request, or by a different customer, is refused rather than answered with the earlier order. A **wrong skill answer creates nothing at all** (ADR-0030): no order, no spent key, basket and hold intact, and the correct option never leaves the API. **`order_number` is `HV-` + 10 base32 characters**, random and never sequential (the length ADR-0031 left to this task). **Phase 5 ends here:** the order is `awaiting_payment`, the reservation stays active and its tickets stay `reserved`; payment, webhooks and `reserved → sold` remain Phase 6. Note the status name — B7 says `awaiting_payment` where the planning prose said "pending_payment"; the specification wins because Phase 6 implements its transitions literally. Run `pnpm db:migrate up` and `pnpm db:codegen`. Next free migration number: `0017`.

- **ADR-0032 — checkout request identity.** The specification does not define whether a checkout request describes the purchase or simply means "convert my basket", and the two readings disagree about what reusing an `Idempotency-Key` means. The owner settled it: **checkout requests are self-describing.** `CreateOrderRequest` now carries `items: [{ slug, quantity, optionId? }]` instead of `answers`, the server matches that intent against the locked basket and refuses a mismatch with a generic conflict, and the idempotency digest covers **market, buyer, terms version and the sorted draw/quantity/answer tuples** — so the same key used for a different quantity, draw, answer or terms version is refused rather than answered with the earlier order. The request remains **intent only**: price, currency, market, availability, ownership, eligibility and answer correctness still come from PostgreSQL. **No schema change** — migration `0016` is unchanged.

- **P5-6:** Migration `0015_market_terms` and per-market terms (B12, ADR-0031). `terms_versions` (per market, `UNIQUE(market_id, version)`, **immutable and never withdrawn once published**), `terms_acceptances` (**append-only**; `user_id` **or** `guest_session_id`, exactly one, the same resolution ADR-0031 applied to cart ownership) and `market_settings.active_terms_version_id` with a composite FK so a market cannot point at another market's terms. **The active version gates checkout, not market enablement** — `hv_market_missing_settings` is untouched, so a market with no terms is still enabled and browsable but cannot take an order; `GET /markets/:market/terms` reports that as `checkoutAllowed`. New routes: `GET /markets/:market/terms`, `POST …/terms/acceptance`, and admin `GET/POST /admin/markets/:market/terms` plus `…/:terms/publish` and `…/:terms/activate` (`markets.gate.manage`, sensitive, audited). **No legal wording is stored or invented** — there is no content column; the content is legal's and arrives in Phase 12. Accepting checks the version the customer saw against the active one, so a stale page cannot record agreement to wording nobody was shown. Run `pnpm db:migrate up` and `pnpm db:codegen`. Next free migration number: `0016`.

- **Testing:** the integration test template now reproduces the production privilege model (`ALTER DEFAULT PRIVILEGES FOR ROLE hv_owner`). Previously `hv_app` had **no** privileges in any test database, so every assertion that it cannot DELETE or UPDATE an append-only table passed for the wrong reason — there was no grant to revoke, and a migration that forgot its REVOKE would have looked correct.

- **P5-5:** Migration `0014_carts` and the server-side basket (B4, ADR-0026, ADR-0031). `carts` is owned by exactly one signed-in customer **or** one guest session, one per owner per market (two partial unique indexes, because the owning column differs); `cart_items` holds a reservation and deliberately **does not copy** its quantity, price or currency. **Market isolation is structural**: composite foreign keys make a UK basket holding an IE draw unrepresentable, not merely refused, and a guard trigger stops a basket holding somebody else's reservation. New routes `GET /markets/:market/cart`, `POST …/cart/items`, `DELETE …/cart/items/:item`, all `@Public({ identify: true })` behind `MarketGuard` — **a verified guest can now hold tickets without an account**, while the authenticated reservation routes are unchanged and still refuse a guest cookie. Adding a draw allocates through the existing `TicketAllocator`, so there is one allocation path, one set of caps and one lock order. New rate limit `cartItemsPerOwner` (30 per 10 minutes, the same value as `reservePerUser`). Guest → user cart merge is **not** implemented, per ADR-0031. Run `pnpm db:migrate up` and `pnpm db:codegen`. Next free migration number: `0015`.

- **Phase 5 scope lock (documentation only):** the remaining Phase 5 work is now broken down as **P5-5** (guest checkout access + per-market basket, migration `0014`), **P5-6** (market terms versions and acceptance, `0015`), **P5-7** (order creation, skill answer and idempotency, `0016`) and **P5-8** (integration and gate hardening). Scope, dependencies, per-task constraints and a **committed Phase 5 Definition of Done** are in [PROJECT_STATUS.md](../PROJECT_STATUS.md). **ADR-0030** settles the wrong-skill-answer behaviour, which was previously recorded in three places that disagreed. The P4 handoff's instruction that "Phase 5 marks the reservation's tickets `reserved → sold`" is **superseded**: under Option A that is Phase 6. **P5-5 is next and is not approved to start.**

- **Phase 5 checkout decisions (documentation only):** **ADR-0031** records the owner's decisions on the three questions the scope lock left open, so P5-5, P5-6 and P5-7 are no longer blocked. **Cart ownership:** a cart carries `user_id` and `guest_session_id` with a CHECK that exactly one is set, plus one `market_id` — so "one cart per owner per market" is two partial unique indexes, and `hvAuth`/`hvGuest` stay as separate in the schema as ADR-0029 keeps them in the guard. **Terms:** an active terms version gates **checkout**, not market enablement — a market can be enabled and browsable without one but cannot take an order; content stays Phase 12 and is never invented. **`order_number`:** `HV-` plus an uppercase alphanumeric suffix, randomly generated, `UNIQUE`, never the primary key, never sequential; the length is P5-7's to choose. Cart-merge-on-sign-in is explicitly **not** decided — nothing requires it, so it is a P5-5 implementation decision.

- **P5-4:** Migration `0013_guest_email_verifications` and guest email verification (ADR-0020). A six-digit code, stored only as its SHA-256, valid 10 minutes, usable once, with 5 attempts counted under a row lock, 3 sends per address per hour and 20 per IP per hour (the same value as registration). New public routes under `/markets/:market/checkout/email` (`POST code`, `POST verify`, `GET verification`); the first request issues the guest session, so these are the only routes that set `hv_guest`. This is the **first producer** for the outbox: the payload is sealed (ADR-0028) and delivered by the P5-2 relay, so no plaintext code exists in PostgreSQL or Redis. **`OUTBOX_ENCRYPTION_KEY` is now required by the API as well as the worker, and must be the same value in both**, or codes cannot be opened. Two shared pieces moved so the producer can reach them: `enqueueOutboxEvent` from `apps/worker` to `@hv/db`, and the verification-email topic and payload type to `@hv/domain` — both old paths re-export, so no caller changed. Run `pnpm db:migrate up` and `pnpm db:codegen`. Next free migration number: `0014`.

- **P5-3:** Migration `0012_guest_sessions` and guest identity for checkout (ADR-0029). An opaque token stored only as its SHA-256, carried in a separate `hv_guest` cookie, lasting 24 hours, with a slot for the verified email that is a guest’s ticket-cap key (normalized exactly as `users.email`, good for 30 minutes). It is **not authentication**: the guard resolves it only on public routes, and it cannot satisfy any authenticated or admin route. New optional env: `GUEST_SESSION_TTL_HOURS`, `GUEST_VERIFIED_EMAIL_TTL_MINUTES`. Run `pnpm db:migrate up` and `pnpm db:codegen`. Next free migration number: `0013`.

- **P5-2:** Mail delivery for the outbox (ADR-0028). The `outbox` queue now RELAYS to a new `notifications` queue keyed by the outbox row id (specification B17); the notifications worker sends the message and only then marks the row published, so `published_at` still means delivered. Provider-independent `MailPort` with an SMTP adapter (Mailpit in dev/test; production provider is still O14 and a production worker without mail configuration refuses to start). Verification-code payloads are sealed with AES-256-GCM, so no plaintext one-time code is stored in PostgreSQL or Redis. New worker env: `SMTP_URL`, `MAIL_FROM`, `OUTBOX_ENCRYPTION_KEY`, `OUTBOX_ENCRYPTION_KEY_ID`. No migration; next free number is still `0012`.

- **P5-1:** Migration `0011_outbox`: transactional outbox (`outbox` table, guard trigger, `hv_claim_outbox`). Producers add an event with `enqueueOutboxEvent` inside their own transaction, so it commits or rolls back with the business change; the worker claims due events every 5 s with `FOR UPDATE SKIP LOCKED` and delivers them at least once. No producers or handlers yet (P5-2). Run `pnpm db:migrate up` and `pnpm db:codegen`. Next free migration number: `0012`.

- **P5-0:** Migration `0010_reservation_end_fix`: `hv_end_reservation` now returns the entrant-cap allowance for the ticket rows it actually freed (`GET DIAGNOSTICS`), not the reservation quantity, so tickets that are already sold keep counting against the cap (NB-1). Behaviour is unchanged for Phase 4 and Phase 5, where nothing writes `sold`. Run `pnpm db:migrate up`. Next free migration number: `0011`.
